# J5.3 — Concurrence et invariant métier : capacité d'une séance

## Objectif

Passer d'un compteur simple à un état métier partagé. Une séance possède un nombre maximal de places. Plusieurs threads peuvent tenter de réserver simultanément : le nombre de places réservées ne doit jamais dépasser la capacité.

Cet exercice montre pourquoi remplacer un champ par un AtomicInteger ne suffit pas toujours : la règle métier porte sur une opération composée qui doit rester cohérente dans son ensemble.

## Contrat

Implémente TrainingSessionCapacity dans le package com.clementlh.labs.concurrency :

- le constructeur reçoit une capacité strictement positive ;
- boolean reserve(int places) réserve les places si elles sont disponibles, sinon retourne false ;
- une demande non positive doit être rejetée par IllegalArgumentException ;
- int reservedCount() retourne le nombre de places réservées ;
- la capacité ne change pas après construction.

## Scénario concurrent

Le test simule 20 workers qui tentent chacun 100 réservations d'une place, alors que la capacité vaut 100.

Résultat attendu :
- exactement 100 réservations réussies ;
- reservedCount() == 100 ;
- aucune réservation ne fait dépasser la capacité.

Le CountDownLatch coordonne le départ ; il ne protège pas l'état métier.

## Travail demandé

1. Implémente d'abord la version la plus simple sans synchronisation et explique pourquoi elle est incorrecte.
2. Ajoute la protection nécessaire pour rendre atomiques la vérification de la capacité et la mise à jour du nombre réservé.
3. Fais passer les tests.
4. Ajoute au moins un test sur une capacité invalide et un sur une quantité de réservation invalide.
5. Dans JOURNAL.md, explique pourquoi un AtomicInteger seul ne suffit pas à garantir l'invariant si la lecture, la vérification et l'écriture sont séparées.

## Questions de compréhension

1. Quelle est précisément la section critique dans reserve ?
2. Pourquoi synchroniser seulement reservedCount() ne résoudrait-il pas le problème ?
3. Pourquoi deux compteurs atomiques ne garantissent-ils pas automatiquement un état cohérent ?
4. Quelle différence fais-tu entre thread-safe et respect des invariants métier ?
5. Dans une application Spring, pourquoi un verrou Java ne protège-t-il pas contre une seconde instance de l'application ou plusieurs pods ?
